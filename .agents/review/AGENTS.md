# 代码审查规范

这是由[顶层入口](../../AGENTS.md)路由的跨目录任务规范。适用于代码审查、回归审计、架构精简评估和缺陷归因；审查的组件规范仍需读取。

## 从产品入口建立审查范围

- 确认审查基线、目标分支 / 提交和是否包含未提交改动。用户问“是否由这次重构引入”时，基线是重构前版本，不是任意选取的上一个提交。
- 列出本次涉及的真实入口：Cursor 原生模型请求、External API、模型测试、账号操作、接管操作、TAB 或 Commit。不要把一个入口的问题泛化到全部入口。
- 沿入口追到修改点，再追到输出与收尾：调用者、参数来源、协议分支、开关、锁、取消令牌、数据写入与所有者。已有上层校验与生命周期约束必须纳入判断。
- 先检查回归和用户可见行为，再检查模块职责。不要以统一风格、减少行数或增加防御为理由要求独立重构。

## 发现问题前必须回答

| 要点 | 必须说明的证据 |
| --- | --- |
| 预期 | 当前需求、界面承诺、已支持协议或已有测试要求什么行为 |
| 入口 | 用户通过哪个功能、何种配置到达这段代码 |
| 触发 | 具体输入或操作顺序；哪些条件真实可达，哪些是测试人为制造的 |
| 影响 | 输出、工具执行、连接、持久化、诊断或资源中的哪一项出错 |
| 来源 | 新增回归、清理前已有、设计限制，还是尚未确认 |
| 证据 | 实际客户端、真实 HTTP 入口配模拟上游、模块测试或静态分析 |

缺少关键入口或影响证据时，作为待验证候选记录，不把它写成已确认的产品 bug。静态证据足以证明可达错误时不强求昂贵复现，但必须写出推导链。

## 复现的证据边界

- 推荐先用真实路由和配置配合本地模拟上游复现，再用最小单元测试定位。真实服务商请求不是验证每个网关 bug 的必要条件。
- 使用人工锁、屏障、延迟或直接丢弃 future 可以研究并发，但必须解释真实程序中谁会持锁、谁会取消、对应窗口如何出现。
- 替换业务处理器为原子变量，只证明调度顺序；手工组装内部状态，只证明该状态下的函数行为。二者都不能直接证明完整桌面流程存在同等故障。
- 区分“取消令牌已触发”“HTTP 已断开”“本地 Worker 已停止”和“远端停止计算”。观察到其中一项，不能声称全部成立。
- 不以未复现判定不存在，也不以复现一次宣称高频。没有线上数据时，不编造触发频率或概率。
- 复现脚本不修改真实账号、用户安装、证书或日常数据库。临时插入测试前保存原文件，结束时只恢复自己的改动；发现文件被同时修改时不得覆盖。

## 分类与优先级

先区分产品功能 bug、诊断 / 观测缺陷、兼容范围限制和健壮性建议，再评严重程度。

| 等级 | 使用条件 |
| --- | --- |
| P0 | 已证实的严重数据损坏、安全事故或产品普遍不可用，需要立即处理 |
| P1 | 已证实在当前支持的入口和合理操作下造成重大功能、数据或资源影响；说明为何必须优先 |
| P2 | 支持场景中可达、影响明确的局部功能错误，按正常维护修复 |
| P3 | 影响轻微的诊断错误，或触发条件受限且证据充分的低风险边界 |
| 待验证 / 健壮性建议 | 真实入口、触发可能性或实际影响尚未证实，不进入阻塞性缺陷清单 |

- 人工并发测试失败不自动构成 P1；日志状态错误不自动等于推理失败。低频也不自动降级，已证实的数据损坏或安全影响仍需按后果处理。
- 普通 Cursor 主链、账号插件路径和可选 External API 分开评级。一个受支持的外部 API 缺陷仍是 bug，但不声称原生 Agent 普遍受损。
- 不追求发现数量。普通路径和必要边界覆盖后，没有证据支持的候选可以不报告；不要不断扩大故障注入来制造新一轮工作。

## 归因与报告

- 对每项报告检查 `git diff` / `git show`，必要时用相同入口对照基线。区分行为原先就错、此次扩大了影响、此次新增了错误；代码移动不是引入时间。
- 不能把“当前版本复现”说成“旧版也运行过同样测试”。归因仅基于历史代码时明确说明。
- 报告先列需处理的实际问题，写明优先级、入口、触发条件、影响、归因和精确代码位置。健壮性建议单独放置，避免淹没产品缺陷。
- 建议首先是最小修正和对应回归用例，不顺势提出通用状态机、持久化补偿层或新配置，除非实际需求证明它们必要。
- 对误判或过高评级直接更正。所有结论都可被新证据推翻，不为维持前次结论而扩大定义。
- 审查默认不修代码；已有明确修复授权时按授权范围继续。结束时说明验证范围、未验证部分及工作区是否被修改。
